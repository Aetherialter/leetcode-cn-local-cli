# 技术决策记录

最近更新：2026-07-31

本文记录当前源码已经采用或现有产品文档已经确认的技术选择，并说明替代方案和可能的调整方向。它不替代 [产品边界与待定决策](PRODUCT_BOUNDARIES.md)：仍处于待定状态的行为不会在本文中被写成结论。

## 状态定义

- **当前采用**：当前源码和发行版已经使用，但可以在 `0.x` 阶段迁移。
- **产品确认**：产品边界已经明确，后续实现不能擅自改变。
- **目标方向**：设计草案已提出，但当前源码尚未实现。
- **待决策**：必须由维护者拍板后才能进入相关实现。

## 已做技术选择

### TD-001：Python 3.12+ 与 `src` 包布局

状态：当前采用

选择：项目声明 `requires-python = ">=3.12"`，源码位于 `src/leetcode_local_cli/`，命令入口为 `lc = "leetcode_local_cli.cli:run"`。

为什么选择：

- `src` 布局可以避免测试无意中从仓库根目录导入未安装源码，减少打包遗漏。
- Python 3.12 允许项目使用现代类型语法和标准库能力，并缩小早期兼容测试范围。
- Console Script 让 uv、pip 和 pipx 安装后都能提供统一的 `lc` 命令。

替代方案：

- 把包直接放在仓库根目录，结构更少，但更容易掩盖安装包配置问题。
- 支持更旧 Python，用户范围更大，但需要扩大 CI、依赖和语法兼容成本。

未来调整：

- `Python >=3.12` 目前没有上限；`PB-012` 尚未确定 v1.0 的正式小版本矩阵。
- v1.0 前需要用实际 CI 覆盖决定支持范围，不能仅依赖元数据声明。

### TD-002：uv 负责锁定、构建与工具安装

状态：当前采用

选择：使用 `uv.lock`、`uv run`、`uv build` 和 `uv tool install`，构建后端为 `uv_build`。

为什么选择：

- 单一工具覆盖依赖锁定、开发命令、构建和 CLI 隔离安装。
- 安装器可以复用 `uv tool`，避免项目维护独立虚拟环境生命周期。
- 锁文件为开发和 CI 提供可复现依赖集合。

替代方案：

- Poetry、PDM 或 Hatch 可以提供类似项目管理能力。
- 标准 `venv + pip + build` 依赖更少，但需要更多脚本和环境约定。

未来调整：

- 官方推荐仍可保持 uv，但长期设计要求标准 pip 和 pipx 也能使用发行包。
- 安装器未检测到 uv 时只提示官方文档，不自动下载或执行远端脚本；这是已确认的安全边界。

### TD-003：Typer 命令行与 Rich 终端展示

状态：当前采用

选择：Typer 负责命令、参数和退出；Rich 负责表格、Panel、spinner 和状态颜色。

为什么选择：

- Typer 基于类型注解定义 CLI，当前命令规模下实现成本低。
- Rich 能快速提供跨平台、可读的题目列表、Doctor 和判题结果。

替代方案：

- `argparse` 没有第三方运行时依赖，但命令结构和帮助维护更手工。
- Click 与 Typer 能力接近，但类型注解集成更弱。
- Textual 等 TUI 框架交互更强，但会显著增加状态、终端和自动化复杂度。

未来调整：

- UI 技术形态尚未冻结；长期设计要求先比较普通 CLI、TUI 或组合方案。
- 无论选择何种 UI，核心层都不能依赖 Typer 或 Rich，非 TTY 和重定向输出必须可用。

### TD-004：同步 `httpx.Client` 与结构化错误分类

状态：当前采用

选择：使用同步 `httpx.Client`、固定超时和上下文管理器；通过 `ClientResult`/`ClientErrorKind` 区分网络、HTTP、JSON、结构和认证错误。

为什么选择：

- CLI 请求量低，同步模型更简单，不需要维护同步/异步双接口。
- 结构化错误比把 httpx 异常和 traceback 直接暴露给用户更稳定。
- `httpx.MockTransport` 允许不访问真实站点就验证协议边界。

替代方案：

- Requests API 更传统，但 MockTransport 和同步/异步统一能力较弱。
- 全异步客户端可提高并发吞吐，但当前没有批量请求或后台同步需求。
- 直接抛出原始 httpx 异常实现最少，但会把传输细节变成公共契约。

未来调整：

- 长期仍保持同步优先。
- `ClientResult.data: Any` 只是过渡实现；目标是结构化模型和项目自有异常层级。
- 提交轮询应从固定次数迁移为总超时和可配置轮询间隔。

### TD-005：当前只支持 LeetCode 中文站

状态：当前采用

选择：基础 URL、GraphQL、提交路径、Cookie 域和界面文案都面向 `leetcode.cn`。

为什么选择：

- 早期先完成一个真实站点的端到端流程，避免在协议尚不稳定时过早抽象。
- 中文站符合当前产品名称和主要用户工作流。

替代方案：

- 从首版同时支持 `.cn` 与 `.com`，覆盖更广，但认证、接口、题目内容和错误差异会放大早期复杂度。
- 通过散落的域名条件判断支持双站点，短期快，但长期难以测试和隔离凭据。

未来调整：

- v1.0 目标是正式支持中文站和国际站。
- 站点差异应通过内部适配协议表达；两个站点的账号、Cookie 和配置必须严格隔离。

### TD-006：Chrome Cookie 自动读取与手动 Cookie 兜底

状态：当前采用

选择：使用 `browser-cookie3` 读取 Chrome Cookie，检查域名边界和两个必要 Cookie；失败时通过 `getpass` 手动输入。

为什么选择：

- 复用浏览器登录态可以避免实现 LeetCode 密码、验证码和多因素认证流程。
- 手动输入为浏览器数据库不可读、解密失败或平台不兼容提供可控兜底。
- `getpass` 避免 Cookie 在终端回显。

替代方案：

- 要求用户始终手动粘贴，依赖更少但体验较差。
- 实现账号密码登录会增加安全责任，并可能不兼容验证码和站点策略。
- 浏览器扩展可以提供更稳定交互，但超出当前轻量 CLI 范围。

未来调整：

- 长期计划增加 Edge 和 Firefox。
- 浏览器异常只应忽略已知环境错误，意外编程错误不能被静默吞掉。

### TD-007：单题、单文件工作区

状态：产品确认，v0.8 继续采用

选择：用户配置指向的默认工作区中的 `solution.py` 是唯一主要工作文件；`lc solve` 表示切换题目，可以无确认覆盖普通文件。当前实现拒绝非普通目标并使用同目录随机临时文件原子替换。

为什么选择：

- 刷题路径短，用户可以立即编辑和测试。
- 不需要工作区索引、数据库、目录命名或归档策略。
- 与当前轻量、在线优先定位一致。

替代方案：

- 每题独立目录利于历史保存，但会引入命名、迁移、发现和清理规则。
- 在用户级缓存中维护解法可以减少工作区文件，但不符合普通编辑器工作流。

未来调整：

- v0.8 的单个默认工作区已经确认；它是否成为 v1.0 长期模型仍需在 API 冻结前审查。
- 当前实现已拒绝符号链接、断链、目录和 reparse point；无论未来采用何种布局，该边界都不得放宽。
- 排他创建和原子替换已完成，后续继续补充平台级竞争条件验证。

### TD-008：marker 定义远程提交区域

状态：当前采用

选择：生成文件写入题目元数据，并只提交 `# @lc submit_begin` 与 `# @lc submit_end` 之间的代码。

为什么选择：

- marker 外的本地辅助代码不会被发送到 LeetCode。
- 提交不需要重新解析 Python AST 或猜测 `Solution` 类边界。
- 前端展示题号与内部提交 ID 分开保存，避免提交到错误题目。

替代方案：

- 提交整个文件实现简单，但会携带本地测试代码。
- AST 提取可以更智能，但面对注释、辅助类型、顶层函数和不完整代码时规则复杂。
- 每次提交重新请求题目信息会减少本地元数据，但增加网络依赖和目标漂移风险。

未来调整：

- marker 名称是否允许自定义尚未决定。
- `PB-004` 将决定提交前校验整个文件、marker 区域还是不做本地编译。

### TD-009：冻结 dataclass 表示部分结构化数据

状态：当前采用

选择：题目摘要、题目详情、工作区元数据、检查结果等使用 `@dataclass(frozen=True)`；远端客户端的大部分成功结果仍是字典。

为什么选择：

- 冻结模型减少流程中意外修改，并给类型检查器提供明确字段。
- dataclass 属于标准库，不增加重量级运行时依赖。
- 允许项目逐步从松散字典迁移，而不要求一次性重写。

替代方案：

- `TypedDict` 只提供静态约束，运行时仍是可变字典。
- Pydantic 提供强校验和序列化，但会增加依赖和模型语义。
- 全部保留字典实现快，但公共 API 难以稳定和发现。

未来调整：

- 目标是账号、分页、提交和错误也使用明确模型。
- 凭据模型必须使用安全 `repr`，避免 Cookie 因调试输出泄露。

### TD-010：默认工作区中的 Session JSON

状态：v0.8 阶段性采用，长期需要替换

选择：Session 以 UTF-8 JSON 保存到显式默认工作区的 `.leetcode_local_cli/session.json`。不再根据命令启动目录定位，也不迁移或删除旧 `.aether_lc/session.json`。POSIX 上设置目录 `0700` 和文件 `0600`，写入使用随机同目录临时文件和原子替换。

为什么选择：

- 维护者需要把一个明确的 Session 文件交给 AI，在授权条件下验证真实账号和远程提交全流程。
- 当前没有旧版本用户，不需要为迁移增加复杂度和数据破坏风险。
- 显式工作区至少消除了 Session 随命令启动目录漂移的问题，原子写入同时修复固定临时文件目标风险。

替代方案：

- Windows Credential Manager、macOS Keychain 和 Linux Secret Service 更适合秘密，但跨平台封装与不可用场景更复杂。
- 环境变量不落盘，但对日常 CLI 工作流不方便，也可能通过进程环境泄露。
- 仅进程内使用安全性更高，但每次启动都要重新输入。

影响与未来调整：

- Session 仍是明文秘密，不得输出、提交、同步或放入共享工作区。
- v0.8 不声称已经完成秘密与工作区分离；Windows Credential Manager、macOS Keychain 和 Linux Secret Service 延后重新设计。
- 真实提交必须由维护者明确授权，自动化 CI 继续只使用假 Cookie 和 MockTransport。

### TD-011：Doctor 默认不执行工作区代码

状态：产品确认

选择：`lc doctor` 默认只静态检查 `solution.py`；只有显式 `--run-solution` 才启动 Python 子进程，并使用 10 秒超时。

为什么选择：

- Doctor 是诊断命令，用户不应因为查看环境状态而隐式执行工作区代码。
- 工作区可能来自不可信仓库，默认执行会扩大本地代码执行风险。
- 显式参数保留了需要运行验证时的能力和用户意图。

替代方案：

- Doctor 始终执行可以发现更多运行问题，但破坏最小副作用原则。
- Doctor 永不执行更安全，但需要用户另行运行 `lc test`。

未来调整：

- 默认不执行的边界应保持。
- `PB-002` 尚需决定显式运行时是否永久保持静默以及显示多少错误信息。

### TD-012：系统关联打开生成的 Python 文件

状态：产品确认的当前兼容行为

选择：Windows 使用 `os.startfile`，macOS 使用 `open`，Linux 使用 `xdg-open`；打开失败在部分平台被静默忽略。

为什么选择：

- 不需要预先配置编辑器，生成后可快速进入编辑流程。
- 跨平台实现较短，满足早期单文件工作流。

替代方案：

- 只打印路径最安全、最可预测，但少一步便利。
- `--open` 显式启用能表达用户意图。
- 配置编辑器参数数组能准确启动编辑器，但需要配置优先级和跨平台解析规则。

未来调整：

- `.py` 系统关联在 Windows 上可能是 Python 解释器而非编辑器。
- 长期应提供显式编辑器配置或 `--open`，并禁止通过 Shell 拼接命令；具体模型等待 `PB-007`。

### TD-013：外部终端文本一律按纯文本处理

状态：当前采用，长期安全原则

选择：来自远端接口、工作区和用户输入的字符串先过滤不安全控制字符，再构造 Rich `Text`；外部数据不解释为 markup 或样式。

为什么选择：

- 避免恶意标题、用户名或文件内容注入颜色、伪造状态或 OSC 8 超链接。
- 样式由本地 UI 结构化指定，数据和展示控制明确分离。

替代方案：

- Rich 自动转义可以覆盖部分 markup，但仍需处理控制序列和未来 UI 后端。
- 完全关闭颜色最安全但损失可读性，而且仍不等于控制字符安全。

未来调整：

- 即使以后改为 TUI 或其他渲染器，这一信任边界也必须保留。
- 需要继续测试合法标记、畸形标记、ANSI 和 OSC 输入。

### TD-014：无数据库、无完整题面持久化

状态：产品确认，适用于 v1.0 前基础 CLI

选择：当前在线获取题目，不引入 SQLite、PostgreSQL、Redis 或完整本地题库。

为什么选择：

- 保持安装和运行轻量，避免迁移、并发、备份和数据合规问题。
- 当前用户主流程不需要本地数据库也可以完成。
- 避免在工作区模型和长期产品方向未稳定时过早固化数据结构。

替代方案：

- JSON 缓存实现简单，但并发、升级和局部查询能力有限。
- SQLite 适合单机数据，但会引入 schema 和迁移生命周期。
- 云数据库支持跨设备，但会引入账号、权限、隐私、成本和部署责任。

未来调整：

- 轻量缓存是否以及何时实现，以 `DEVELOPMENT_PLAN.md` 和长期设计的后续明确阶段为准。
- v1.0 后可评估可选数据库，但基础 CLI 不应因此获得强制数据库依赖。

### TD-015：pytest 分层测试与无真实凭据 CI

状态：当前采用

选择：使用 pytest、monkeypatch、临时目录、Typer `CliRunner` 和 `httpx.MockTransport`；CI 不保存真实 LeetCode Cookie。

为什么选择：

- 单元和协议边界测试可重复，不受账号、网络、限流和站点数据变化影响。
- 临时目录避免测试覆盖用户工作区。
- MockTransport 能验证状态码、JSON 和响应结构，而不伪装成真实端到端测试。

替代方案：

- CI 真实请求更接近生产，但不稳定、有凭据泄露和远端副作用风险。
- 只做手动测试成本低，但难以回归安全边界。

未来调整：

- 增加适配器契约、打包、公开 API 和跨平台测试。
- 真实登录和提交只能作为明确授权的手动发布候选验收，不能把 mock 结果描述为真实集成通过。

### TD-016：标签驱动发布与 PyPI Trusted Publisher

状态：当前采用

选择：`v*` 标签触发 GitHub Actions；三系统验证通过后，使用 OIDC Trusted Publisher 上传 PyPI，再创建 GitHub Release。

为什么选择：

- 不在仓库或 GitHub Secrets 中保存长期 PyPI Token。
- 标签、版本和 Release Notes 提供可审计发布边界。
- 跨平台安装器在发布前验证，降低只在开发机可用的风险。

替代方案：

- 手动本地上传更直接，但凭据和构建环境难以审计。
- API Token 自动发布兼容广，但需要保存和轮换长期秘密。
- 每次 main push 自动发布速度快，但误发布和版本治理风险高。

未来调整：

- 增加普通 push/PR CI，标签工作流继续只负责更严格的发布门禁。
- v1.0 前需要验证 uv、pip、pipx 以及 wheel、源码包的一致安装体验。

### TD-017：显式默认工作区与安装后初始化

状态：已接受并在 v0.8 实现

日期：2026-07-30

选择：使用不可变 `AppPaths` 统一用户配置、工作区配置、`solution.py` 和 Session 路径。普通命令只使用用户配置中的默认工作区，不提供全局 `--workspace`。`lc init` 无参数时交互输入父目录并追加固定目录名，显式路径表示完整工作区，`--yes` 只服务于明确路径的自动验收。

为什么选择：

- uv 工具环境只安装程序，不能承载用户解法和登录文件；显式默认工作区使安装位置与数据位置解耦。
- 当前只有单工作区真实需求，引入全局覆盖选项会提前扩大公开 API。
- 安装脚本可以调用绝对 `lc init`，无需依赖当前终端立即刷新 PATH。
- 重复初始化必须幂等，版本更新才能验证并复用已有工作区而不触碰用户代码。

替代方案：

- 继续使用 `Path.cwd()` 最简单，但命令从不同目录执行会读写不同数据，uv 安装后体验不可靠。
- 每条命令都要求 `--workspace` 最明确，但日常使用冗长，也超出当前单工作区范围。
- `uv tool install` 自动执行 post-install 不可行；Python 包安装流程不提供项目自定义交互钩子。

影响：

- `--help`、`--version` 和 `lc init` 不要求已有工作区；其他命令缺少有效配置时明确失败。
- 官方安装脚本只在可交互终端调用 `lc init`，CI 和重定向环境跳过并打印手动命令。
- 初始化保留已有普通 `solution.py`；只有 `lc solve` 继续按产品边界覆盖普通文件。
- 配置采用版本 1 的严格 TOML 模型，损坏、未知字段或不支持版本不会被自动覆盖。

验证：跨平台路径单元测试、配置与初始化测试、CLI `init` 测试、安装脚本测试、完整质量门禁和构建后入口 smoke test。

### TD-018：同目录随机临时文件与原子替换

状态：已接受并在 v0.8 实现

日期：2026-07-30

选择：覆盖 `solution.py`、用户配置和 Session 时，先验证目标是普通文件或不存在，再在同目录排他创建随机临时文件，完整写入、flush、fsync 后重新验证并使用 `os.replace`。初始化新文件使用排他创建并在失败时只回滚本次创建内容。

原因：同目录替换才能获得主要平台的原子 rename 语义；随机排他临时文件避免固定 `.tmp` 被预先占用；替换目录项不会跟随目标符号链接，失败时旧文件保持不变。

替代方案：直接 `open(..., "w")` 代码少，但会先截断旧文件且存在链接跟随和部分写入风险；固定临时文件仍可被目标劫持。

影响：原子替换会产生新 inode，现有普通文件内容和目标路径语义保持，符号链接、目录、junction 和 reparse point 继续拒绝。

### TD-019：持久 worker 执行 `Solution` 的交互输入

状态：已接受并在当前源码实现，待发布

日期：2026-07-31

选择：`lc test` 不再要求用户维护 `run_cases()` 或写预期输出。CLI 启动一个 UTF-8 无缓冲的独立 Python worker，加载 `solution.py` 后按 `Solution.__dict__` 的定义顺序选择首个不以 `_` 开头的实例方法。交互输入是受限的 `name = value` 参数赋值；`--stdin` 使用相同格式读取多行输入并输出 JSON Lines。每次调用都创建新的 `Solution` 实例；默认每组调用独立限制 1 秒，超时终止 worker，下一组调用前自动重启。输入错误、异常与超时不会中断交互，但最终退出码为 1；所有调用正常结束才返回 0，且不声称算法正确。

为什么选择：

- 用户能快速观察真实返回值，不必把每组输入硬编码到工作区文件；仍可在确认解法后直接提交，两条工作流互不绑架。
- `Solution.__dict__` 保留类体定义顺序，入口约定简单、无需解析用户键入的方法名；私有命名约定让递归辅助函数不被误选。
- `ast.literal_eval` 支持刷题常见的容器与标量，同时不执行用户输入；JSON 行协议为 AI/CI 提供稳定、可解析的机器输出。
- 独立子进程隔离用户代码异常、退出和卡死；逐组计时比一次总计时更符合连续交互，超时后的重启避免 worker 留在未知状态。

替代方案：

- 保留 `run_cases()` 加 assert 可以表达预期结果，但要求用户编辑模板、容易遗忘或误删入口，且空实现曾造成假通过。
- 每组新建一个子进程的隔离更强，但连续交互的启动成本高，也无法在超时后只重启受影响 worker。
- 在当前进程中导入并调用方法更容易保留对象，但用户代码可以污染 CLI 进程、调用 `sys.exit` 或永久阻塞。
- 强制 `lc submit` 先运行本地调用会阻止用户跳过本地调试，而且无预期输出的调用不等同于远端判题正确性。

影响：

- 新生成模板不再生成 `run_cases()`；空函数签名和 LeetCode 内联 `: pass` 会转换为显式 `NotImplementedError`。这样模板既不触发“声明了返回值却默认返回 None”的类型检查噪声，也不会在 `lc test` 中以 `null` 假装成一次成功调用。
- 1 秒预算以每次调用为单位；worker 初次加载与超时后重启也受同一保护，但不声称复现远端题目或其他语言的时间限制。较慢用例需要显式提高 `--timeout`。
- `lc test` 仍会执行用户文件顶层代码和被发现的方法，不是安全沙箱；只能在可信工作区中运行。
- 交互用户输出经过现有终端控制字符过滤，不把内容解释为 Rich markup 或终端控制序列；JSON Lines 输出由 JSON 编码转义。
- `lc doctor --run-solution` 保持原有整文件诊断语义；`lc submit` 继续只读取 marker 区域。

验证：单元和 CLI 测试覆盖安全字面量、元组/字典协议、首个公开入口、私有与后续辅助方法、每组新实例、返回值、原地修改、异常、异步与缺失入口、超时后重启、交互退出、JSON Lines stdin、非法超时参数、非 UTF-8 和提交不触发本地执行。

### TD-020：`solution.py` 采用严格 UTF-8 解码边界

状态：已接受并在当前源码实现，待发布

日期：2026-07-31

选择：生成文件继续使用无 BOM UTF-8；读取用户 `solution.py` 时使用 `utf-8-sig`，因此同时接受标准 UTF-8 和 UTF-8 BOM。其他编码通过共享 `solution_source.py` 转换为专用错误；不猜测编码、不替换非法字节、不自动转换或改写文件。

为什么选择：

- 项目生成、Git、JSON 提交和现代 Python 工具链都以 UTF-8 为稳定共同边界。
- UTF-8 BOM 是 Windows 编辑器的常见输出，`utf-8-sig` 可以兼容它而不扩大到不确定的本地编码。
- 猜测编码可能在不同机器得到不同结果；替换非法字节可能改变 Python 语义或把乱码代码发送到远端。
- 只读检测保证修复错误边界时不会引入覆盖用户代码的新副作用。

替代方案：

- `tokenize.open()` 可支持 Python 编码声明，但会让工作区正式支持 GBK 等多种编码，并增加 runner、静态检查和远端提交的一致性成本。
- `errors="replace"` 能避免异常，但可能把损坏内容误判为合法代码，违反防假通过和数据完整性要求。
- 自动检测并重写 UTF-8 对用户更省步骤，但检测不可靠，且未经确认修改用户文件不符合当前安全边界。

影响：

- `inspect_solution_file()` 使用独立 `INVALID_ENCODING` 状态，不把编码错误误报为权限问题。
- 内部 worker 使用共享严格解码边界读取源码；解码失败时不会启动用户代码。
- 编码失败时 `lc test` 不启动 worker，`lc doctor --run-solution` 不执行文件，`lc submit` 不加载凭据、不创建客户端、不发送请求。
- 普通 CLI 只显示转换为 UTF-8 的受控提示，底层异常通过异常链保留给开发诊断但不进入用户输出。

验证：测试覆盖非法字节的静态检查、CLI test、Doctor、内部 worker 和提交短路，以及包含 UTF-8 BOM 的有效解题文件和本地交互执行。

### TD-021：远程提交退出码表达最终判题结果

状态：已接受并在当前源码实现，待发布

日期：2026-07-31

选择：`lc submit` 继续先展示完整判题结果，但机器退出码只在明确获得 `status_msg == "Accepted"` 时为 0。所有非 Accepted、轮询超时、缺少可识别状态、网络、认证和响应错误返回 1；命令使用错误返回 2。

为什么选择：

- 用户可以直接阅读终端文案，但 Shell、CI 和 AI 只能可靠地依据退出码判断成功。
- “请求成功发送”不代表解法正确；该命令会等待判题，因此成功语义应表达最终 Accepted。
- 轮询超时意味着结果未知，不能在未证明通过时返回成功。
- 退出码不会关闭终端或阻止用户继续输入，只修复自动化契约。

替代方案：

- 请求成功发送就返回 0，适合异步提交命令，但会与当前等待并展示最终判题的交互语义冲突。
- 为 Wrong Answer、超时、认证等分配多个不同非零码能表达更多信息，但当前消费者只需要成功与未成功，过早扩展会增加公共契约。
- 让 UI 渲染函数返回成功布尔值实现更短，但会把业务判定责任放进展示层。

影响：

- CLI 在渲染后检查原始提交结果；UI 输出、颜色和返回终端的体验不变。
- `dict | None` 仍是过渡结果类型，后续领域模型阶段应替换为结构化 `SubmissionOutcome`。
- 固定 10 次轮询仍不是稳定总超时；本决策只修复最终退出语义，不把轮询次数问题伪装为已完成。

验证：CLI 测试覆盖 Accepted、Wrong Answer、Time Limit Exceeded、缺少状态字段和轮询超时，并确认所有结果都会先交给 UI 渲染。

## 已知过渡实现，不应被视为长期决策

以下行为是当前源码事实，但长期设计已经明确要消除：

- `service.py` 直接导入 `typer.Exit` 和 UI 输出函数。
- 客户端成功结果和账号资料仍大量使用裸字典。
- CLI 有的命令经过 service，有的直接调用 auth、client 或 workspace。
- 提交轮询使用固定 10 次、每次 0.5 秒的循环。

修复这些问题时应提供迁移步骤和测试，不应以“清理代码”为名一次性重写全部模块。
