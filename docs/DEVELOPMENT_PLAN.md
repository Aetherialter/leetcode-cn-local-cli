# 开发计划

最近更新：2026-08-01

本文件只维护当前执行顺序，不再为长期设想预分配版本号。已发布历史见 [release-notes](release-notes/)，长期方向见 [PROJECT_DESIGN](PROJECT_DESIGN.md)。每项工作开始前仍需重新完成需求分析、方案确认和验收设计。

## 优先级

### P0：可靠性闭环

1. **提交总超时**
   - 用单调时钟控制完整判题等待预算，不再依赖固定轮询次数。
   - 保留当前退出码契约：仅 `Accepted` 为 0，其余为 1，命令用法错误为 2。
   - 覆盖慢判题、未知状态、单次请求超时、节流和终止状态。
2. **Git 工作区标记决策**
   - 明确 `.leetcode-local-cli.toml` 是共享文件、本机文件还是应迁移位置。
   - 未确认前不自动修改任意仓库的 `.gitignore`。
3. **日常 CI**
   - 普通 push/PR 运行 Ruff format、Ruff lint、Pyright 和 pytest。
   - 标签工作流继续负责三平台构建、安装器、包 smoke test 和发布。

### P1：核心边界

- 将业务结果从裸字典迁移为小型不可变模型。
- 将核心错误从 `typer.Exit` 和直接 Rich 输出迁移为项目异常或结构化结果。
- 让 CLI 只负责参数、交互、渲染和退出码；核心逻辑不依赖 Typer/Rich。
- 在真实消费者出现后再提供最小 Python API，不预先设计庞大公共接口。

### P2：体验与加固

- 决定 `test --verbose`、Doctor 输出、提交前静态校验和编辑器配置。
- 处理 Broken Pipe、合法空分页和实际支持的 Python 小版本。
- 评估依赖审计、静态安全扫描和更完整的秘密扫描。
- 设计 `ListNode`、`TreeNode` 等 LeetCode 类型转换，但不污染基础字面量协议。

## 暂不进入

- 数据库、完整题库、多题归档和后台同步。
- Web、桌面 GUI、AI 功能和多语言提交。
- 国际站、系统秘密存储、题面图片等方向，只有在当前可靠性与核心边界稳定后才重新立项。

## 每项工作的完成标准

1. 行为与 [PRODUCT_BOUNDARIES](PRODUCT_BOUNDARIES.md) 一致；待定语义先确认。
2. 使用满足需求的最小可维护改动，不顺带重构无关模块。
3. 覆盖成功、失败、边界和副作用；真实凭据或远端提交只做明确授权的手动验收。
4. 相关 Ruff、Pyright、pytest、构建或入口检查通过。
5. 更新状态；只有架构、边界、安全或重大选择变化时才更新对应专题文档。
