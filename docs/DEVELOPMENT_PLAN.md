# 长期开发计划

最近更新：2026-07-28

本文把当前源码、安全审计、产品边界和长期设计整理为可执行顺序。它不替代具体功能开始前的需求分析，也不擅自决定 [产品边界与待定决策](../PRODUCT_BOUNDARIES.md)中的开放问题。

## 路线依据

当前存在两份不同年代的路线：

- [ROADMAP](../ROADMAP.md)把 `v0.9`、`v0.10` 分别规划为缓存和样例提取。
- 较新的 [PROJECT_DESIGN](../PROJECT_DESIGN.md)把 `v0.9`、`v0.10` 分别规划为 Python API 预览和双站点客户端。

在路线正式统一前，本计划采用以下原则：

1. 已确认的安全边界优先于新增产品功能。
2. 待定行为先决策、再实现，不能由当前缺陷行为反向定义产品。
3. `v0.8` 以后以较新的总体设计作为架构方向，但版本号和公开 API 仍需逐阶段审查。
4. 缓存、样例提取、图片、UI 大改等能力不能抢在路径、凭据和核心边界之前。

## 功能优先级

### P0：已完成的写入目标边界

- 拒绝 `solution.py` 符号链接、断链、目录、目录链接和 Windows reparse point。
- 保证错误信息不暴露不必要的内部 traceback，并且不会把实际写入位置伪装为工作区目标。

该项已于 2026-07-28 完成。实现保持普通文件覆盖行为，写入前拒绝所有静态可识别的非普通目标，并把校验和写入异常转换为无 traceback 的 CLI 错误。它不包含 `PB-005` 尚未决定的原子写入事务。

### P1：下一个稳定版本的阻断项

- 拍板并实现工作区写入事务，覆盖随机临时文件、排他创建、原子替换和失败后原文件保证。
- 拍板并实现 `lc test` 的执行契约、超时和输出策略。
- 拍板并实现远程提交退出码和轮询总超时。
- 继续收敛非 UTF-8、编辑器打开失败和其他工作区异常；`lc solve` 的写入权限与占用错误已完成映射。
- 设计用户配置目录、系统秘密存储和旧 Session 迁移。
- 为普通分支和 Pull Request 增加 CI。

### P2：持续加固

- 增加显式编辑器配置，逐步替代系统文件关联。
- 处理 Broken Pipe、极端分页和受支持 Python 小版本范围。
- 增加依赖漏洞、Bandit 和秘密扫描门禁。
- 补齐打包内容、公开类型声明和文档示例执行测试。

### 暂不进入

- 数据库和完整本地题库。
- 多题目录或自动归档，直到工作区模型被确认。
- 自动样例提取和轻量缓存，直到核心路径与产品路线统一。
- Web、桌面 GUI、AI、后台同步和 Python3 以外的提交语言。

## 后续迭代计划

### 阶段 0：路线与决策收口

#### 目标

让维护者、源码、测试和文档使用同一组产品语义，避免在修复过程中意外冻结错误行为。

#### 工作内容

- 统一 `ROADMAP.md` 与 `PROJECT_DESIGN.md` 对 `v0.9` 以后阶段的定义。
- 为即将修改的功能逐项确认 `PB-*` 决策。
- 以 `docs/PROJECT_STATUS.md` 作为当前进展入口，但不复制所有历史版本细节。
- 为安全或架构决策保留日期、适用版本、替代方案和迁移影响。

#### 完成标准

- 下一项功能没有未解决且会改变实现方向的产品问题。
- README、产品边界、开发计划和验收标准没有相互冲突。

### 阶段 1：工作区写入安全

#### 目标

在不改变当前“普通 `solution.py` 可无确认覆盖”的产品行为下，阻断工作区外写入和写入失败导致的数据破坏。

#### 建议拆分

1. [已完成] 只读识别并拒绝符号链接、断链、目录和 reparse point。
2. [已完成] 为 POSIX 和 Windows 建立可测试的目标分类边界。
3. 在 `PB-005` 拍板后，引入同目录随机临时文件、排他创建和原子替换。
4. [部分完成] 权限和占用异常已转换为结构化工作区错误；打开编辑器失败的语义仍等待 `PB-005`。
5. 为 Session 临时文件处理复用同类安全原则，但不固化即将废弃的工作区 Session 位置。

#### 完成标准

- 普通不存在文件和普通现有文件符合已确认覆盖语义。
- 非普通目标在写入前被拒绝，目标和链接指向内容均保持不变。
- 写入失败后的数据保证符合 `PB-005` 最终结论。
- 测试覆盖现存链接、断链、目录、只读目标、序列化/写入失败和临时文件清理。
- Windows junction 已通过实际文件系统测试；Windows 符号链接测试在无创建权限的环境中显式跳过，并由 POSIX 测试覆盖链接与断链行为。

### 阶段 2：本地测试契约

#### 目标

让“本地测试通过”具有稳定、可解释的含义，避免空执行或无限执行被误判。

#### 前置决策

- `PB-001`：`run_cases()` 的定义和调用责任。
- `PB-002`：stdout、stderr、简化异常和 verbose traceback。
- `PB-006`：解题文件编码。

#### 工作内容

- 明确 CLI 是执行整个文件、验证入口，还是显式调用测试函数。
- 避免模板入口与 CLI 重复执行 `run_cases()`。
- 为 `lc test` 增加明确总超时和超时退出行为。
- 保持子进程参数数组调用，不引入 `shell=True`。
- 区分语法错误、编码错误、启动失败、断言失败、非零退出和超时。

#### 完成标准

- 缺少测试入口不会再产生未定义的“通过”语义。
- 成功、断言失败、运行时异常、超时和编码问题都有测试和稳定退出码。
- `lc doctor --run-solution` 与 `lc test` 的职责和输出差异被文档明确说明。

### 阶段 3：提交语义与可靠性

#### 目标

让命令行退出状态准确表达提交和判题结果，并把固定轮询次数改为可解释的总超时。

#### 前置决策

- `PB-003`：最终判题与退出码。
- `PB-004`：提交前静态校验。

#### 工作内容

- 为 Accepted、非 Accepted、请求失败、认证失败和轮询超时定义结果模型和退出映射。
- 使用总超时和轮询间隔，而不是仅用 10 次固定循环推断超时。
- 明确哪些请求可以安全重试，限制重试次数，并尊重服务端节流信息。
- 保证提交前校验绝不隐式执行用户代码。
- 继续展示前端题号、标题和 slug，使用内部提交 ID 发起请求。

#### 完成标准

- Shell 和 CI 可以只通过退出码区分 Accepted 与失败。
- 所有终止状态、超时和接口结构异常都有测试。
- 真实提交只在维护者明确授权的手动验收中执行，CI 不保存真实 Cookie。

### 阶段 4：日常 CI 与质量门禁

#### 目标

把当前只在标签发布时运行的质量检查前移到普通开发流程。

#### 工作内容

- 普通 push 和 Pull Request 运行格式、Lint、Pyright 和 pytest。
- 标签工作流继续执行三系统构建、安装器、wheel、源码包和发布检查。
- 根据维护成本增加依赖审计、Bandit 和秘密扫描。
- 保持第三方 GitHub Actions 固定到明确提交 SHA。
- 清晰区分跨平台自动化测试和需要真实浏览器/凭据的手动验收。

#### 完成标准

- 未通过日常门禁的提交不能进入发布准备。
- 发布任务不依赖真实 LeetCode 凭据。
- 检查失败不会通过跳过、移除或弱化测试解决。

### 阶段 5：v0.8 运行上下文、配置与工作区基础

#### 目标

消除导入时当前目录状态，正式分离工具安装、用户配置、凭据和工作区。

#### 前置决策

- `PB-008`：工作区根目录和初始化语义。
- `PB-009`：秘密存储不可用时的降级。
- `PB-007`：如果本阶段引入编辑器配置，必须先确定配置优先级和命令模型。

#### 工作内容

- 引入 `AppPaths` 或等价显式运行上下文。
- 所有工作区函数显式接收根目录或文件路径。
- 实现不会锁死长期工作区模型的最小 `lc init [path]`。
- 定义跨平台用户配置目录和系统秘密存储入口。
- 安全迁移旧 `.leetcode_local_cli/session.json`，全过程不输出 Cookie。

#### 完成标准

- 导入包不再固定 `Path.cwd()`。
- 从任意目录运行时，所有文件只写到解析后的目标位置。
- 凭据不再默认落入普通项目工作区。
- 旧 Session 能安全迁移，或给出明确且不泄密的人工操作提示。

### 阶段 6：领域模型、异常与 Python API 预览

#### 目标

建立不依赖 Typer、Rich 和松散成功字典的可复用 Python 核心。

#### 工作内容

- 新建独立模型、异常和 API 门面，但只公开已有真实消费者需要的类型。
- 使用冻结 dataclass 或等价不可变模型表示账号、题目、分页、提交和诊断结果。
- 使用结构化异常替代核心层的 `typer.Exit` 和直接 UI 输出。
- 让 CLI 逐步通过应用用例或公开 API 使用核心能力。
- 在发行包中提供 `py.typed`，增加顶层导出和 API 契约测试。

#### 完成标准

- 核心模块不导入 Typer 或 Rich。
- Python 示例可以从构建后的 wheel 导入并执行纯逻辑。
- 公开成功结果不使用裸 `dict`。
- Pyright 能识别公开模型、异常和返回类型。

### 阶段 7：双站点与 CLI 迁移

#### 目标

通过显式站点适配器，使中文站和国际站共享应用用例与公开模型，同时严格隔离账号和 Cookie。

#### 工作内容

- 建立内部站点适配协议及 CN/Global 实现。
- 支持 Chrome、Edge、Firefox 和手动 Cookie 兜底。
- 为登录、状态、列表、详情、模板、提交、判题和 Doctor 建立适配器契约测试。
- 将所有 CLI 命令迁移到统一应用层，删除重复业务路径。

#### 完成标准

- 相同公开方法可操作两个站点。
- 任一站点请求都不会携带另一站点 Cookie。
- CLI 和 Python API 对相同输入产生等价业务结果。
- 真实双站点登录、题目获取和授权提交只在明确手动验收中完成。

### 阶段 8：题面、UI、源码收口与 v1.0 验收

#### 目标

在核心 API 稳定后完善题面结构与跨终端体验，最后停止新增功能并完成架构收口。

#### 顺序

1. 结构化题面文档块和图片纯文本降级。
2. 普通 CLI、TUI 或组合方案的独立原型与决策。
3. UI 实施，保持非 TTY、重定向、无颜色和窄终端可读。
4. 删除迁移期重复模型、错误映射、路径处理和轮询逻辑。
5. 冻结公开 API，完成 uv、pip、pipx、三系统和双站点验收。

#### 完成标准

以 [PROJECT_DESIGN 总体验收清单](../PROJECT_DESIGN.md#18-总体验收清单)为准。数据库、AI、Web、多语言提交和后台同步不属于 `v1.0` 范围。

## 每个功能的开发节奏

每个功能使用以下顺序，避免把代码生成当作工程实践：

1. 需求分析：问题、用户价值、边界和验收标准。
2. 技术设计：涉及模块、数据流、失败路径、方案与替代方案。
3. 教学实现：先解释思想和核心片段，由开发者完成主体实现。
4. Review：检查正确性、架构、命名、维护性、性能和安全，优先让开发者自行修正。
5. 验证：运行与风险匹配的格式、Lint、类型、测试、构建或启动检查。
6. 总结：记录学习内容、新增能力、修改文件、设计决策和后续方向。
7. 状态维护：更新 `PROJECT_STATUS.md`；重大架构或产品选择同时更新本计划和 `TECH_DECISIONS.md`。
